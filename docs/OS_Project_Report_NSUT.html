1. Introduction

1.1 Background & Motivation

In modern multiprogrammed and time-sharing computer systems, the Central Processing Unit (CPU) is the core computational resource that must be shared efficiently among multiple concurrently running processes [1]. The fundamental objective of CPU scheduling is to multiplex processor execution cycles across active tasks to optimize system throughput, minimize process turnaround and waiting times, maximize CPU utilization, and provide responsive interactive latency [2]. Although the theoretical principles of CPU scheduling are extensively covered in academic literature [1]-[3], students frequently encounter substantial conceptual friction when attempting to visualize dynamic runtime phenomena. Static textbook timing diagrams fail to illustrate low-level operational realities, including process lifecycle state transitions, hardware context-switch latency, cache cold-start penalties, and multi-burst asynchronous I/O interleaving [4], [5].

1.2 Problem Statement & Educational Challenges

Traditional pedagogical approaches rely on manual, pencil-and-paper Gantt chart calculations for small, idealized process workloads. This methodology suffers from severe limitations when addressing complex, dynamic operating system behaviors:

  • State Machine Opacity: Manual tracing cannot demonstrate the discrete tick-by-tick state transformations of a Process Control Block (PCB) across NEW, READY, RUNNING, WAITING, and TERMINATED states [1].
  • Context Switch Overhead Neglect: Textbook exercises generally assume instantaneous CPU switching, completely ignoring the non-negligible latency required for hardware register preservation, page-table base updates, and TLB invalidation [5].
  • I/O-Wait Interleaving: Students struggle to compute metrics for multi-burst tasks that alternate between CPU execution bursts and asynchronous I/O blocking intervals [7].
  • Tooling Deficiencies: Existing web-based scheduling toys frequently couple scheduling logic directly into user-interface event handlers, precluding automated unit testing and creating non-deterministic tie-breaking bugs [10].

1.3 Project Objectives & Key Deliverables

To overcome these pedagogical and engineering shortcomings, this project accomplishes the following core deliverables:

  • Decoupled Core Engine: Design and implement a strictly decoupled simulation engine authored in pure TypeScript with zero UI or browser DOM dependencies, executing discrete clock ticks ($t = 0, 1, 2, \dots$).
  • State Machine Integrity: Enforce a rigorous 5-state process lifecycle state machine with legal transition validation and runtime illegal transition detection [1].
  • Comprehensive Scheduling Suite: Implement seven canonical scheduling algorithms: FCFS, Non-Preemptive SJF, Preemptive SRTF, Round Robin (with dynamic time quantum), Preemptive Priority, Non-Preemptive Priority (with starvation prevention via dynamic aging), and 3-Tier Multi-Level Feedback Queues (MLFQ) [1], [3].
  • Realistic Hardware Simulation: Faithfully model hardware context-switch cost overhead ticks and multi-burst I/O operations.
  • Interactive Visualization Dashboard: Develop a modern React 19 visualizer featuring tick-by-tick time travel scrubbing, color-coded Gantt chart generation, live ready queue inspection, and side-by-side comparative benchmarking.
  • Automated Verification Harness: Achieve complete mathematical correctness validated through an exhaustive automated test suite of over 200 unit and integration tests [10].

1.4 Scope of the Work

The scope of this project encompasses discrete-event single-core processor simulation, process lifecycle management, hardware latency modeling, interactive timeline replay, and empirical metric benchmarking. The software is designed to serve as an authoritative pedagogical framework for students, instructors, and system developers studying operating system process scheduling mechanisms.

2. Literature Survey

2.1 Evolution of CPU Scheduling & Queueing Models

CPU scheduling research traces back to early queueing theory and operations research for industrial job shops [8], [9]. In early batch computing architectures, jobs were processed sequentially using First-Come, First-Served (FCFS) policies [1]. As multiprogramming systems emerged in the 1960s, researchers demonstrated that non-preemptive Shortest Job First (SJF) is mathematically optimal for minimizing average waiting times, provable via the classic exchange argument [8]. However, Kleinrock [8] and Coffman [9] established that SJF is impractical for general-purpose operating systems because future CPU burst lengths cannot be known a priori without predictive heuristics.

2.2 Comparative Study of Classical Scheduling Policies

Silberschatz et al. [1] and Tanenbaum and Bos [2] provide foundational analyses of the primary CPU scheduling algorithms:

  • First-Come, First-Served (FCFS): Simple FIFO queue discipline. Demonstrates severe vulnerability to the Convoy Effect, where short processes are trapped behind long CPU-bound tasks [1].
  • Shortest Job First (SJF): Dispatches the job with the smallest burst. Optimal for average waiting time but susceptible to starvation of long tasks [1], [8].
  • Shortest Remaining Time First (SRTF): Preemptive variant of SJF. Preempts the running job whenever a newly arrived task possesses a strictly smaller remaining burst [2].
  • Round Robin (RR): Designed for time-sharing systems by allocating equal time slices (quantum $q$). Tanenbaum [2] highlights that quantum selection presents a fundamental trade-off: small $q$ incurs severe context-switch thrashing, while large $q$ degenerates into FCFS.
  • Priority Scheduling: Allocates CPU according to static or dynamic priorities. Vulnerable to indefinite postponement (starvation), which requires dynamic aging mechanisms [1].
  • Multi-Level Feedback Queue (MLFQ): Introduced by Corbato on the Compatible Time-Sharing System (CTSS) and refined in BSD Unix [3], [6]. Employs multiple prioritized queues, automatically demoting CPU-bound jobs to lower tiers and prioritizing interactive I/O jobs.

2.3 Contemporary OS Schedulers (Linux CFS, FreeBSD MLFQ)

Modern production operating systems have transitioned from simple heuristics to sophisticated scheduling architectures. Robert Love [4] and Bovet and Cesati [5] document the evolution of the Linux kernel scheduler from the $O(1)$ multi-queue scheduler to the Completely Fair Scheduler (CFS). Linux CFS models an ideal multi-tasking CPU on hardware by maintaining a virtual runtime (vruntime) metric inside a time-ordered red-black tree [4]. In BSD Unix and early macOS kernels, MLFQ variants with dynamic decay-based priority adjustment were standard [3], [6]. These commercial implementations highlight the importance of dynamic priority adjustment, starvation prevention, and hardware context-switch accounting.

3. Methodology

3.1 Steps: Decoupled Architecture & 7-Step Clock Tick Loop

The architecture of the simulator is founded upon strict modular decoupling between the simulation core (src/engine/) and the visualizer (src/components/). The simulation engine maintains discrete integer simulation time ($t = 0, 1, 2, \dots$). At each clock tick, the engine executes an invariant 7-step sequence governed by simulator.ts:

  • Step 1 - Admit Arrivals (NEW → READY): All processes in the NEW state with $\text{arrivalTime} \le t$ are identified. The state machine transitions each process from NEW to READY and invokes scheduler.onArrival() to place it into the active queue structure [1].
  • Step 2 - Update I/O Wait Queue (WAITING → READY): All processes blocked in the waitingQueue decrement their ioCountdown. Any process whose countdown reaches 0 transitions from WAITING to READY and calls scheduler.onArrival() [7].
  • Step 3 - Handle Context Switch Delay: If a hardware context switch is in progress (csCountdown > 0), the countdown decrements, an explicit Idle Overhead tick is recorded on the Gantt timeline, and the clock advances without executing user instructions [5].
  • Step 4 - Evaluate Preemption: If a process is currently executing on the core, the engine invokes scheduler.shouldPreempt(running, ctx). If preemption is signaled, the process transitions from RUNNING to READY, is returned to the queue, and running is cleared to null [1], [2].
  • Step 5 - CPU Core Dispatch: If the CPU core is idle, scheduler.pickNext(ctx) selects the optimal ready job. If config.contextSwitchCost > 0 and a new task is dispatched, the job is buffered and context-switch idle ticks are scheduled [5].
  • Step 6 - Execute 1 Clock Tick: The active running process executes for 1 clock tick: remainingTime is decremented, cpuTicksDone is incremented, and total busyTicks is updated. A complete discrete system snapshot is appended to the historical ledger [10].
  • Step 7 - Handle Completion / I/O Blocking: The process is inspected: if cpuTicksDone matches an scheduled I/O burst trigger, it transitions to WAITING and enters the waitingQueue [7]. If remainingTime == 0, it transitions to TERMINATED and records $\text{completionTime} = t + 1$ [1].

3.3 Algorithms: Algorithmic Formulations

The mathematical and procedural logic for all implemented scheduling algorithms is formalized below:

ALGORITHM 1: Simulation Engine Discrete Tick Loop

Function SimulationTick(t, ctx):
  1. For each p in ctx.allProcesses where p.state == NEW and p.arrivalTime <= t:
       transition(p, READY); ctx.scheduler.onArrival(p, ctx)
  2. For each p in ctx.waitingQueue:
       p.ioCountdown--
       If p.ioCountdown == 0: transition(p, READY); ctx.scheduler.onArrival(p, ctx)
  3. If ctx.csCountdown > 0:
       ctx.csCountdown--; RecordIdleTick(t); Return
  4. If ctx.running != null and ctx.scheduler.shouldPreempt(ctx.running, ctx):
       transition(ctx.running, READY)
       ctx.scheduler.onArrival(ctx.running, ctx)
       ctx.running = null
  5. If ctx.running == null:
       nextJob = ctx.scheduler.pickNext(ctx)
       If nextJob != null:
         If ctx.config.contextSwitchCost > 0 and nextJob != ctx.lastRunning:
           ctx.csCountdown = ctx.config.contextSwitchCost - 1
           ctx.pendingProcess = nextJob; RecordIdleTick(t); Return
         ctx.running = nextJob; transition(ctx.running, RUNNING)
  6. If ctx.running != null:
       ctx.running.remainingTime--; ctx.running.cpuTicksDone++; ctx.busyTicks++
       RecordSnapshot(t, ctx)
  7. If ctx.running != null:
       If CheckIOTrigger(ctx.running): transition(ctx.running, WAITING); ctx.running = null
       Else If ctx.running.remainingTime == 0: transition(ctx.running, TERMINATED); ctx.running.completionTime = t + 1; ctx.running = null

ALGORITHM 2 & 3: FCFS and Non-Preemptive SJF

FCFS.pickNext(ctx):
  Return ctx.readyQueue.dequeue() // Strict FIFO order based on arrival

SJF.pickNext(ctx):
  Return ctx.readyQueue.dequeueMin(comparator: (a, b) => {
    If a.burstTime != b.burstTime: Return a.burstTime - b.burstTime
    If a.arrivalTime != b.arrivalTime: Return a.arrivalTime - b.arrivalTime
    Return a.pid.localeCompare(b.pid)
  })

ALGORITHM 4: Shortest Remaining Time First (SRTF)

SRTF.shouldPreempt(running, ctx):
  shortestReady = ctx.readyQueue.peek()
  If shortestReady == null: Return False
  // Strict inequality prevents context-switch thrashing on equal remaining time
  Return shortestReady.remainingTime < running.remainingTime

ALGORITHM 5: Round Robin with Deterministic Arrival Ordering

RoundRobin.shouldPreempt(running, ctx):
  ctx.quantumTicksUsed++
  If ctx.quantumTicksUsed >= ctx.timeQuantum:
    If ctx.readyQueue.isEmpty():
      ctx.quantumTicksUsed = 0; Return False // Renew quantum without penalty
    ctx.quantumTicksUsed = 0; Return True    // Preempt and rotate
  Return False

// Invariant: At tick t, Step 1 enqueues newly arriving processes BEFORE
// Step 4 appends the preempted running process to the tail of readyQueue.

ALGORITHM 6: Priority Scheduling with Dynamic Aging

Priority.onTick(ctx):
  If ctx.config.enableAging and (ctx.currentTick % ctx.config.agingInterval == 0):
    For each p in ctx.readyQueue:
      If p.priority > 0: p.priority-- // Promote towards highest priority (0)

ALGORITHM 7: Multi-Level Feedback Queue (MLFQ)

MLFQ Architecture:
  - Queue 0: Round Robin with quantum q = 4 (Highest Priority)
  - Queue 1: Round Robin with quantum q = 8 (Medium Priority)
  - Queue 2: First-Come, First-Served (Lowest Priority, Long Compute)

MLFQ.onQuantumExhausted(p):
  p.queueLevel = min(p.queueLevel + 1, 2) // Demote to lower queue tier

MLFQ.onPeriodicBoost(ctx):
  Every boostInterval ticks (e.g. 50 ticks):
    For all processes across all queues: p.queueLevel = 0 // Prevent Starvation

6. Discussion

6.1 Trade-Offs in Time Quantum Selection

Our empirical results in Section 5 validate the theoretical trade-offs described by Tanenbaum and Bos [2]. When the Round Robin time quantum is configured too small (e.g., $q = 1$ or $q = 2$), context-switch frequency escalates drastically (14 switches in Table 5.3). If a non-zero hardware context-switch cost is configured (e.g. 2 ticks), effective CPU utilization drops precipitously due to idle switching overhead. Conversely, when $q$ is configured excessively large (e.g., $q \ge 10$), Round Robin degenerates into FCFS, causing average waiting time to rise from 7.20 to 11.40 ticks [1].

6.2 Impact of Hardware Context Switch Latency & TLB Invalidation

In physical hardware architectures, switching execution from process A to process B incurs substantial latency [4], [5]. The CPU must flush hardware registers to memory, update kernel process descriptors, reload the memory management page directory register (CR3 / TTBR0), and invalidate the Translation Lookaside Buffer (TLB) [5]. By allowing users to parameterize contextSwitchCost in our simulator, students observe how high preemption frequencies degrade system throughput, instilling an intuitive appreciation for why real kernels (such as Linux) implement minimum granularity heuristics to prevent thrashing [4].

6.3 Starvation Vulnerabilities & Dynamic Aging Solutions

Both SJF and strict Priority scheduling suffer from the risk of indefinite postponement (starvation) [1]. If short or high-priority tasks continuously enter the ready queue, low-priority tasks may never acquire the CPU core. Our simulation results confirm that Dynamic Aging completely eliminates starvation: as waiting time accumulates, priority values increment monotonically, guaranteeing eventual dispatch [1]. Similarly, the periodic global priority boost in MLFQ restores starved compute-bound processes back to Level 0 [3].

6.4 Architectural Decoupling & Engine Robustness

A critical engineering finding of this project is the overwhelming superiority of decoupled architecture. Because src/engine/ contains zero React or DOM dependencies, our automated test suite executes 210 comprehensive test cases in approximately 1 second. Furthermore, this decoupling guarantees that the visualization dashboard acts purely as an observational window, eliminating accidental state mutations during UI rendering [10].

7. Conclusion

This project successfully developed an interactive, discrete-event Single-Core CPU Scheduling Simulator engineered with a pure TypeScript simulation core and a reactive React visualization dashboard. By enforcing a formal five-state process lifecycle model with adjacency validation, the system guarantees architectural integrity and prevents illegal state mutations. Seven canonical scheduling algorithms—FCFS, SJF, SRTF, Round Robin, Preemptive Priority, Non-Preemptive Priority with aging, and a three-tier Multi-Level Feedback Queue—were fully implemented and validated against textbook benchmarks. Physical hardware phenomena, including context-switch latency and multi-burst I/O operations, were accurately modeled, providing critical pedagogical insight into real-world operating system trade-offs. Verified through 210 automated unit and integration tests with zero failures, this simulation framework bridges the gap between abstract scheduling theory and practical implementation, serving as a robust educational platform for computer science students.
