Abstract

Central Processing Unit (CPU) scheduling is one of the most fundamental abstractions in modern multiprogrammed operating systems. While textbook theoretical treatments present scheduling policies using idealized timing diagrams, students and practitioners often struggle to conceptualize dynamic runtime phenomena such as process state transitions, context-switch latency, cache cold-start penalties, I/O-wait blocking bursts, and deterministic tie-breaking under simultaneous events.

In this project, we design and implement a comprehensive, production-grade Single-Core CPU Scheduling Simulator engineered with a strictly decoupled architecture. The core discrete-event simulation engine is developed in pure TypeScript without any UI or DOM dependencies, executing deterministic clock-tick cycles ( = 0, 1, 2, dots$). It models the classical 5-state process lifecycle (NEW, READY, RUNNING, WAITING, TERMINATED) with strict transition adjacency validation, preventing invalid state mutations at runtime.

The simulator implements seven canonical and advanced scheduling algorithms: First-Come First-Served (FCFS), Shortest Job First (SJF Non-Preemptive), Shortest Remaining Time First (SRTF Preemptive), Round Robin (RR with dynamic time quantum and simultaneous arrival resolution), Preemptive Priority, Non-Preemptive Priority (with starvation prevention via dynamic aging), and a 3-tier Multi-Level Feedback Queue (MLFQ with quantum demotion and periodic global priority boost). Hardware-level context switch costs and multi-burst I/O operations are accurately simulated. A responsive React 19 visualizer provides step-by-step timeline scrubbing, dynamic Gantt chart generation, live ready-queue inspection, and side-by-side multi-algorithm comparative analytics. The engine is verified through 210 automated unit and integration tests, ensuring mathematical parity with established operating system literature.

Chapter 1: Introduction & Problem Statement

1.1 Motivation & Background

In modern multiprogrammed and time-sharing computer systems, the Central Processing Unit (CPU) is the primary computational resource. Because typical modern workloads contain multiple concurrent tasks competing for CPU cycles, the operating system kernel must employ sophisticated CPU scheduling policies to multiplex the processor across active processes. The fundamental objective of CPU scheduling is to maximize system throughput, maximize CPU utilization, minimize turnaround and waiting times, and provide deterministic, low-latency response times for interactive user processes.

Computer science students traditionally learn CPU scheduling algorithms through static pen-and-paper Gantt charts. However, static textbook diagrams fail to illustrate several critical operational complexities encountered in real-world systems:

  • Dynamic State Progression: The dynamic progression of process states (NEW → READY → RUNNING → WAITING → TERMINATED) as time ticks forward.
  • Context Switch Costs: The non-negligible cost of hardware context switches, including register saves, page-table base updates, and TLB cache invalidation.
  • I/O-Wait Interleaving: The complex behavior of multi-burst tasks that alternate between CPU computation and asynchronous I/O operations.
  • Simultaneous Event Race Conditions: The exact resolution of simultaneous events, such as when a new process arrives at the identical microsecond that a running process's time quantum expires.

1.2 Problem Definition & Challenges

Existing educational scheduling tools suffer from notable architectural and pedagogical limitations. Many simulators are tightly coupled with specific UI libraries (e.g., mixing HTML DOM manipulation with queue logic), rendering automated testing difficult or impossible. Furthermore, many simulators do not enforce strict process state-machine transitions, allowing processes to jump arbitrarily between states, and ignore physical context-switch latency. Our objective in this project is to develop an industrial-grade, fully verified, discrete-event scheduling simulator that models these low-level operating system realities with absolute mathematical precision.

1.3 Objectives & Key Deliverables

The primary engineering objectives of this project are:

  • Decoupled Core Engine: Architect a pure TypeScript simulation engine strictly decoupled from the presentation layer, capable of executing standalone in Node.js or browser environments.
  • State Machine Integrity: Implement a robust Process Control Block (PCB) state machine with legal transition enforcement and runtime error detection.
  • Algorithmic Diversity: Implement seven core scheduling algorithms: FCFS, SJF (Non-preemptive), SRTF (Preemptive), Round Robin (with configurable quantum), Priority (Preemptive & Non-preemptive with aging), and 3-Level MLFQ.
  • Hardware Overheads & I/O: Model physical context-switch overhead ticks and multi-burst I/O blocking cycles.
  • Interactive Visualization: Provide an interactive React 19 dashboard featuring tick-by-tick time scrubbing, Gantt charts, live ready queue inspection, and comparative multi-algorithm benchmarking.
  • Automated Verification: Establish complete mathematical correctness via a comprehensive automated test suite of over 200 unit and integration tests.

Chapter 2: Operating System Theoretical Foundations

2.1 Process Control Block (PCB) Architecture

In an operating system kernel, each process is represented by a Process Control Block (PCB), also known as a task descriptor in Linux (struct task_struct). The PCB serves as the central repository of information for a specific process. In our simulator, the PCB data structure maintains both static configuration parameters and dynamic execution accounting metrics:

  • Process ID (pid): Unique process identifier (e.g., P1, P2, ...). Used for secondary tie-breaking.
  • Arrival Time (arrivalTime): Simulation clock tick at which the process enters the NEW state.
  • Burst Time (burstTime): Total CPU cycles required for completion.
  • Priority (priority): Integer scheduling priority (lower value represents higher priority by default).
  • Remaining Time (remainingTime): Number of CPU cycles still required until termination.
  • Start Time (startTime): Clock tick at which the process first transitioned to RUNNING.
  • Completion Time (completionTime): Clock tick at which the process transitioned to TERMINATED.
  • I/O Bursts (ioBursts): Array of scheduled I/O blocking intervals specifying after how many CPU ticks an I/O burst begins and how long it lasts.
  • Queue Level (queueLevel): Current queue tier in multi-level feedback scheduling (Level 0, 1, or 2).

2.2 5-State Process Lifecycle State Machine

Our engine models the classic 5-state process lifecycle defined in standard operating system theory (Silberschatz, Galvin & Gagne):

  1. NEW: The process is registered in the system but has not yet reached its arrival clock tick ( < ext{arrivalTime}$).
  2. READY: The process has arrived ( ge ext{arrivalTime}$) and is placed in the scheduler's ready queue, waiting for CPU allocation.
  3. RUNNING: The process currently occupies the single CPU core and is executing instructions.
  4. WAITING: The process is temporarily blocked, waiting for an asynchronous I/O operation to complete.
  5. TERMINATED: The process has completed its total CPU burst ($ ext{remainingTime} == 0$) and has relinquished system resources.

2.3 Transition Invariants & Illegal Transition Handling

To guarantee simulation integrity, the transition() function in src/engine/pcb.ts enforces strict adjacency rules. Any attempt to trigger an illegal state transition immediately throws an explicit runtime error:

Source State Permitted Target States Illegal Mutations (Throws Runtime Error)
NEW READY RUNNING, WAITING, TERMINATED (Cannot bypass admission)
READY RUNNING NEW, WAITING, TERMINATED (Cannot block or terminate without running)
RUNNING READY (Preempt), WAITING (I/O), TERMINATED (Done) NEW (Cannot return to unadmitted state)
WAITING READY (I/O complete) NEW, RUNNING, TERMINATED (Must return to ready queue first)
TERMINATED None (Terminal Sink State) NEW, READY, RUNNING, WAITING (Cannot resurrect terminated jobs)

2.5 Hardware Realities: Context Switch Overhead & TLB Flushes

In physical hardware architectures, switching the CPU from one process to another is not instantaneous. A hardware context switch entails significant operating system overhead:

  • Architectural State Preservation: Saving general-purpose integer and floating-point registers, Program Counter ($), Stack Pointer ($), and processor status flags into the outgoing PCB.
  • Scheduler Execution: Executing kernel scheduler selection routines to determine the next task.
  • Memory Address Space Switch: Reloading the page table base pointer register ($ on x86-64, $ on ARM64) to point to the new process's address space.
  • Cache Invalidation Penalties: Flushing the Translation Lookaside Buffer (TLB) unless tagged ASIDs are enabled, causing an immediate spike in memory translation latency ("cold cache" effect).

Our simulator faithfully reflects this overhead: when config.contextSwitchCost > 0, the engine holds the dispatched process in a pending buffer while advancing the clock through explicit idle overhead ticks. These overhead ticks are recorded in snapshots and color-coded on the Gantt chart.

Chapter 3: Scheduling Algorithms & Mathematical Analysis

3.1 First-Come, First-Served (FCFS) & The Convoy Effect

First-Come, First-Served (FCFS) is the simplest non-preemptive scheduling policy. Processes are dispatched in strict FIFO order according to their arrival time. Once a process acquires the CPU core, it retains control until it yields for I/O or terminates.

Key Vulnerability: Convoy Effect

A major drawback of FCFS where a long CPU-bound process monopolizes the CPU, forcing short, interactive I/O-bound jobs to wait. This causes high average waiting times and leaves I/O peripheral devices completely idle for prolonged periods.

3.2 Shortest Job First (SJF) & Optimality Proof

Shortest Job First (SJF Non-Preemptive) selects the ready process with the smallest total burst time. If two jobs have identical bursts, the tie is broken deterministically by arrival time and then PID.

Theorem (Exchange Argument Proof of Optimality):
Let $ processes execute in an arbitrary permutation with burst times , b_2, dots, b_n$. The total waiting time across all processes is given by: 6516W_{ ext{total}} = sum_{i=1}^{n} (n - i) b_i6516 The weight coefficient $ indicates that the execution of process $ delays all subsequent $ processes. To minimize this weighted sum, the largest coefficients $ must be multiplied by the smallest burst values $. If there exists any adjacent pair where > b_{k+1}$, swapping their order changes total waiting time by $Delta = b_{k+1} - b_k < 0$, strictly reducing total waiting time. Hence, sorting by non-decreasing burst times yields the absolute mathematical minimum average waiting time.

3.3 Shortest Remaining Time First (SRTF)

Shortest Remaining Time First (SRTF) is the preemptive variant of SJF. Whenever a new process arrives, its remaining burst time is compared with the currently running process's remaining time. If $ ext{candidate.remainingTime} < ext{running.remainingTime}$, the running process is immediately preempted and returned to the ready queue.

Preemption Boundary Invariant: If an arriving job has remaining time exactly equal to the running job, the simulator does not preempt. Preemption on equality causes useless context-switch thrashing without reducing remaining execution work.

3.4 Round Robin (RR) & Quantum Selection Trade-offs

Round Robin (RR) is designed specifically for time-sharing systems. Each process is allocated a discrete time slice called a Time Quantum ($). When a running process exhausts its quantum, it is preempted and enqueued at the tail of the ready queue.

  • If quantum $ is very small ( o 0$): System responsiveness is high, but the CPU spends an excessive fraction of time performing context switches instead of productive computation.
  • If quantum $ is very large ( o infty$): Round Robin degenerates into FCFS, re-introducing the convoy effect and high response times for interactive jobs.
  • Simultaneous Arrival Invariant: At discrete clock tick $, if process $ arrives at the exact tick that running process $ exhausts its quantum, $ is enqueued BEFORE $. Arrivals are evaluated in Step 1 while preemption occurs in Step 4.

3.5 Priority Scheduling & Aging Mechanism

Priority scheduling allocates the CPU core to the process with the highest priority (lowest integer value by default). It supports both non-preemptive and preemptive execution modes.

Starvation Resolution: Dynamic Aging

In strict priority scheduling, a steady stream of high-priority processes can prevent a low-priority job from ever running (indefinite postponement). To resolve this, our engine implements Dynamic Aging: every agingInterval clock ticks, all processes waiting in the ready queue have their priority value incremented toward the highest priority until they are dispatched.

3.6 Multi-Level Feedback Queue (MLFQ) 3-Tier Architecture

The Multi-Level Feedback Queue (MLFQ) is the canonical scheduling model used in real operating systems (such as FreeBSD and macOS). Unlike SJF/SRTF, MLFQ requires zero advance knowledge of burst durations, inferring process behavior dynamically:

  • Queue Level 0 (Top Priority): Round Robin with time quantum = 4$. Designed for ultra-fast response for interactive, short-burst jobs.
  • Queue Level 1 (Medium Priority): Round Robin with time quantum = 8$. Intermediate priority for moderately CPU-bound processes.
  • Queue Level 2 (Low Priority): First-Come, First-Served (FCFS). Lowest priority for long, batch compute-intensive processes.
  • Demotion Rule: If a process exhausts its full quantum without completing, it is demoted to $min( ext{Level} + 1, 2)$.
  • Preemption Hierarchy: Any process in Level 0 immediately preempts a running process in Level 1 or 2.
  • Periodic Global Boost: Every boostInterval ticks (default 50), all waiting processes across all tiers are boosted back to Level 0, preventing starvation of CPU-bound tasks.

Chapter 4: System Architecture & Engine Design

4.1 Decoupled Core Architecture

A paramount architectural design requirement of our project was complete structural decoupling between the simulation core and the presentation layer. The entire simulation kernel (src/engine/) is authored in pure, self-contained TypeScript with zero imports from React, HTML DOM, or browser APIs. This architectural separation provides distinct advantages in portability, testing speed, and separation of concerns.

4.2 The 7-Step Simulation Engine Clock Tick Loop

Simulation time advances in discrete integer clock ticks ( = 0, 1, 2, dots$). At each clock tick, the primary simulation method step() in src/engine/simulator.ts executes an invariant 7-step sequence:

  1. Step 1 - Admit Arrivals: Inspect all processes where .state == ext{NEW}$ and .arrivalTime le t$. Transition each to READY and invoke scheduler.onArrival().
  2. Step 2 - Update I/O Wait Queue: Inspect processes in waitingQueue. Decrement ioCountdown. If ioCountdown reaches 0, transition process back to READY and enqueue.
  3. Step 3 - Handle Context Switch Delay: If a context switch is in progress (csCountdown > 0), decrement countdown, log an Idle overhead tick on the Gantt timeline, and advance tick.
  4. Step 4 - Check Preemption: If a process is running, invoke scheduler.shouldPreempt(). If true, transition running job to READY, enqueue it, and set running = null.
  5. Step 5 - CPU Dispatch: If CPU is idle, invoke scheduler.pickNext(). If contextSwitchCost > 0 and switching to a new process, buffer job and initiate context-switch delay.
  6. Step 6 - Execute 1 Clock Tick: Running process executes 1 tick: remainingTime--, cpuTicksDone++, busyTicks++. Record execution snapshot.
  7. Step 7 - Handle Completion / I/O: Check if cpuTicksDone triggers an I/O burst (transition to WAITING) or if remainingTime == 0 (transition to TERMINATED and record completionTime).

4.3 Deterministic Tie-Breaking Specification

To guarantee 100% deterministic, reproducible execution across all algorithms, our queue comparators implement a strict two-tier fallback: primary metric first → arrival time second → PID alphabetically third.
